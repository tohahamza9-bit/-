# المراجعة الأمنية (§14.3) — النتائج والإصلاحات

مراجعة شاملة للكود المالي (نواة Python + جسر Baileys + اللوحة). التمييز بين «مخالفة مؤكّدة» و«تحسين دفاعي».

## 🔴 ثغرتان حرجتان — أُصلِحتا

### 1) إدخال مزدوج عبر «تم» على صفقة `TECH_FAILED`
**السيناريو:** ضُغط «تخزين» فعليًا (المال تحرّك) لكن تحقّق SQL فشل عابرًا → الحالة `TECH_FAILED`
بلا قيد دفتر. الموظف يرى الحوالة محفوظة فيرد «تم» → كان يُعيد الكتابة (الحارس يعتمد الدفتر
الفارغ) → **إدخال مزدوج بأموال حقيقية**. يخالف §8.1 بند 7 و§9.

**الإصلاح** (`core/pipeline.py`):
- **حارس حالة على «تم»** (`_CONFIRM_BLOCKED`): يُرفض على `COMPLETED/ESCALATED/CANCELLED/TECH_FAILED/SELL_DONE`
  → تحويل للمسؤول، لا إعادة كتابة أبدًا.
- **فحص SQL قبل كل «تخزين»** (`_write_jobs`): إن كان الطرف محفوظًا فعلًا في SQL → لا تخزين ثانٍ،
  تسجيل الدفتر فقط (صمّام §9/§11.4/§12 الحقيقي).
- اختبار `test_confirm_on_tech_failed_no_double_entry` يُثبت الحبط.

### 2) `recover_pending` (استرجاع بعد الإطفاء §12) غير موصول — كان كودًا ميّتًا
**السيناريو:** الإطفاء الليلي روتيني (§12). عند العودة يجب فحص SQL لما كان قيد الإدخال قبل أي فعل،
لكن `recover_pending` لم يُستدعَ في بدء التطبيق → خطر ازدواج بعد الإقلاع.

**الإصلاح** (`core/app.py` + `core/db.py`):
- استدعاء `recover_pending(db, verifier)` في `_startup` **قبل** تشغيل العامل؛ وإن فشل الاسترجاع
  لا يبدأ العامل تلقائيًا (يُصعَّد للمراجعة).
- **فهرس فريد جزئي** على الدفتر `(message_key, operation)` حيث `is_reversal=False` — يمنع القيد
  الأصلي المكرّر ذرّيًا على مستوى القاعدة (القيود العكسية مستثناة، تتكرّر لعدّة تعديلات §10).
- backstop في `_append_ledger`: قيد مكرّر → يُسجَّل ويُمنع بلا انهيار.

## 🟡 تحسين دفاعي — طُبِّق ✅
- **مقارنة رمز اللوحة ثابتة الزمن:** `dashboard/app.py` صار يستخدم `secrets.compare_digest`
  بدل `!=` — يتفادى تسريب الفرق الزمني (SEC-002).
